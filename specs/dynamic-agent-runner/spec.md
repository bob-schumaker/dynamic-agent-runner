## Objective

Build a Python library that loads agent workflow artifacts generated by the
agent-development workflow in `clinerules-roschuma`, runs the described workflow
from a user prompt using the official `openai` Python package and a
library-owned tool registry pattern, and returns the final result to the caller.

## Problem Statement

Agent-development artifacts currently describe intended agent workflows, but
this repository needs a runtime library that can consume those artifacts and
execute the workflow consistently. Callers should not need to manually interpret
the definition YAML, Mermaid diagram, optional tool-index metadata, or registry
bindings to run an agent workflow.

## Users

- Developers or automation code that need to execute generated agent workflows.
- Future maintainers implementing the runtime library and its tests.

## Inputs

The library must accept, at minimum:

- an `agent-design.md`-style design document generated by the
  agent-development workflow
- an `agent-runtime.yaml`-style runtime manifest generated by the
  agent-development workflow
- an `agent-graph.mmd`-style Mermaid diagram generated by the same workflow
- tool definitions, either embedded in the runtime manifest under `tools` or
  loaded from an optional reusable `tool-index.yaml`-style external metadata
  catalog
- optional runtime tool overrides that can add, replace, disable, or restrict
  tools globally or for individual `llm_step` nodes without modifying the
  generated agent-design artifacts
- optional built-in default tool packs that can pre-register conservative local
  tools when explicitly enabled by the caller
- a required tool registry argument or approved registry source when the workflow
  is expected to use tools; initial registry support will use this repository's
  own registry abstraction instead of `ai-tools-core`
- bundled or referenced skill support files when the manifest's packaging mode
  requires them
- a user prompt used as the initial request for workflow execution

The expected artifact producers are:

- `/Users/roschuma/Repos/roschuma/clinerules-roschuma/rules/85-agent-development-workflow.md`
- `/Users/roschuma/Repos/roschuma/clinerules-roschuma/skills/agent-development-skill/`

Observed example output artifacts:

- `simple-tool-agent-runtime.yaml`
- `simple-tool-agent-graph.mmd`
- `tool-index.yaml` as an optional reusable metadata catalog

The observed example shape is summarized in this spec so runtime requirements do
not depend on a machine-specific sibling checkout path.

## Output

- The final result of the agent workflow, returned to the caller.
- Errors must be surfaced clearly when artifact loading, validation, tool
  resolution, chat-client execution, or workflow execution fails.

## Functional Requirements

### FR-1: Load generated artifacts

The library must load the design document, runtime manifest, Mermaid diagram,
tool definitions, optional tool registry, and any required skill bundle from
caller-provided paths, already-parsed objects, or raw strings. The recommended
package shape is:

```text
<design-dir>/
  agent-design.md
  agent-runtime.yaml
  agent-graph.mmd
  skill-bundle/
```

The observed example uses `simple-tool-agent-runtime.yaml` as the primary
runtime manifest and references its diagram with `mermaid_diagram:
simple-tool-agent-graph.mmd`.

Acceptance criteria:

- Given valid artifact locations, when the caller loads a workflow, then the
  library reads all required artifacts.
- Given raw strings for the design document, runtime YAML, Mermaid graph, or tool
  index, when the caller loads a workflow, then the library parses those inputs
  without requiring filesystem paths.
- Given already-parsed objects for supported input artifacts, when the caller
  loads a workflow, then the library accepts those objects without reparsing from
  text.
- Given `agent-design.md`, `agent-runtime.yaml`, and `agent-graph.mmd`, when the
  caller loads a package, then the library validates that all three artifacts
  are internally consistent with each other.
- Given a runtime YAML with a `mermaid_diagram` reference, when the caller loads
  a workflow, then the library resolves the referenced Mermaid diagram relative
  to the runtime YAML unless the caller overrides that location.
- Given a missing artifact, when the caller loads a workflow, then the library
  returns or raises an error that identifies the missing artifact.
- Given a manifest with `packaging.mode: hybrid_bundle`, when package loading
  runs, then inline prompt/manifest metadata is loaded from YAML and larger skill
  or support files are resolved from the adjacent bundle paths.
- Given a workflow that requires a reusable `tool-index.yaml`, when the caller
  supplies it as an input, then the library can load the shared metadata catalog
  for validation, documentation, or registry preparation support.
- Given a workflow that references reusable tool-index metadata but the caller
  omits that file, when the callable tool registry contains the required tools,
  then the library can still prepare execution because the registry is
  authoritative for callable tools.
- Given a workflow that includes `available_tools` or `tool_use_step` nodes, when
  execution is requested, then the library requires an explicit tool registry
  argument or another approved registry source before tool invocation is allowed.
- Given caller-provided runtime tool overrides, when the workflow is prepared,
  then the library can add, replace, disable, or restrict tool exposure globally
  or for a specific `llm_step` without requiring changes to the generated runtime
  manifest, tool index, Mermaid graph, or design document.
- Given caller-enabled built-in tool packs, when registry preparation runs, then
  the selected pack's tools are pre-registered in the effective registry but are
  usable only when workflow nodes reference their tool ids.

### FR-1a: Parse runtime manifest sections

The library must parse the required and recommended sections of the generated
runtime YAML manifest for `format_version: 1`.

Acceptance criteria:

- Given required top-level fields `format_version`, `package_type`,
  `package_id`, `entrypoint`, `packaging`, `nodes`, and `edges`, when the
  manifest is loaded, then the library validates their presence before
  execution.
- Given the observed `format_version: 1` and `package_type:
  dynamic_agent_design`, when the manifest is loaded, then the library accepts
  the supported package format or rejects unsupported versions and unsupported
  enum values with a clear error.
- Given manifest metadata such as `package_id`, `name`, `entrypoint`,
  `packaging`, `patterns_present`, and `execution_policy`, when parsing
  succeeds, then that metadata is available to workflow preparation.
- Given `patterns_present` metadata, when parsing succeeds, then the library
  preserves documented pattern identifiers even when the current executor does
  not yet implement pattern-specific adapters.
- Given manifest sections for `state`, `skills`, `tools`, `modes`, `phases`,
  `roles`, `nodes`, `edges`, `output_contracts`, and `validation`, when parsing
  succeeds, then the library preserves the relationships needed for validation
  and execution.
- Given manifest sections for `participant_groups`, `modes`, `phases`, and
  `roles`, when parsing succeeds, then the library preserves the metadata needed
  to represent multi-agent, debate, council-like, workflow-orchestration,
  observer, simulation, memory, speech, computer-use, and other documented
  patterns without inventing new primitive node kinds.

### FR-2: Validate artifact relationship

The library must validate that `agent-design.md`, runtime YAML, Mermaid diagram,
optional tool-index metadata, and the required callable tool registry describe a
coherent workflow before execution begins.

Acceptance criteria:

- Given artifacts that reference incompatible workflow nodes or tools, when the
  workflow is prepared, then execution does not start and the error explains the
  inconsistency.
- Given `agent-design.md` references to the runtime manifest and Mermaid graph,
  when workflow preparation runs, then the referenced artifacts must exist or be
  supplied through equivalent caller inputs.
- Given artifacts whose schemas cannot be interpreted, when the workflow is
  prepared, then the error identifies the artifact and parse/validation failure.
- Given the observed validation rules from the example manifest, when workflow
  preparation runs, then the library checks at least that every node id is
  unique, every edge endpoint references an existing node, every `tool_use_step`
  references an existing callable registry tool, every skill binding references
  an existing skill, every `llm_step` has a prompt or prompt source, and the
  Mermaid graph matches runtime manifest nodes and edges.
- Given an external `tool-index.yaml`, when workflow preparation runs, then the
  library validates its `format_version`, `index_type`, `tools`, and `skills`
  sections when supplied and fails closed for unsupported enum values or
  malformed tool entries, but tool-index presence does not by itself make a tool
  callable.
- Given tool overrides are supplied during workflow preparation, then validation
  verifies that referenced base tools exist when required, added tool definitions
  are schema-compatible with the registry contract, disabled tools are not still
  required by `tool_use_step` nodes, and per-node overrides only target existing
  `llm_step` nodes.

### FR-3: Execute with the official OpenAI Python package

The library must own the default model execution path through the official
`openai` Python package from `https://pypi.org/project/openai/` while leaving
room for callers to pass a protocol-compatible client for tests or alternate
runtime integration. Initial model/client and tool-call support targets OpenAI's
Python SDK directly. `ocihelper` and `ai-tools-core` must not be required by the
initial implementation.

Acceptance criteria:

- Given a prepared workflow and a user prompt, when execution starts, then model
  interaction is routed through a library-owned execution path backed by the
  official `openai` package by default.
- Given a caller-supplied protocol-compatible client, when execution starts, then
  model interaction is routed through that client instead of constructing a
  default client.
- Given a caller-supplied client compatible with the runtime's OpenAI client
  protocol, when execution starts, then the library can use it through the same
  protocol-oriented execution path as the default client.
- Given a model/client failure, when execution is running, then the
  failure is surfaced clearly to the caller.

### FR-3a: Execute manifest node kinds

The library must support the runtime node kinds observed in the example manifest
before claiming compatibility with that example.

Acceptance criteria:

- Given an `llm_step` node with `prompt.system`, `prompt.developer`,
  `prompt.user_template`, `input_vars`, and `output_schema_ref`, when the node
  executes, then the library renders the prompt from available state and calls
  the configured OpenAI client protocol.
- Given a `tool_use_step` node with `tool_id`, `inputs_from`, `outputs`, and
  `failure_behavior`, when the node executes, then the library resolves the tool
  through the library-owned tool registry pattern and records its output state or
  applies the configured failure behavior.
- Given a `decision_step` with an `llm_route` decision contract, when the node
  executes, then the library chooses one of the allowed paths and follows the
  matching outgoing edge.

### FR-3b: Apply runtime tool overrides

The library must support caller-provided runtime tool overrides as part of the
repository-owned registry preparation path. Overrides let callers adapt tool
availability for a run without regenerating or editing the agent-design package.

Acceptance criteria:

- Given additional tool definitions supplied outside the generated manifest or
  optional `tool-index.yaml`, when registry preparation runs, then the library
  can expose those registered tools to eligible `llm_step` nodes and convert them
  to OpenAI tool schema.
- Given a replacement definition for an existing tool id, when registry
  preparation runs, then the library uses the replacement for schema exposure and
  invocation dispatch while preserving clear provenance that the generated tool
  definition was overridden.
- Given a disabled tool id, when registry preparation runs, then the tool is not
  exposed to model calls and cannot be invoked unless a later explicit override
  re-enables or replaces it.
- Given a per-`llm_step` override, when that node is prepared for execution, then
  the node-level tool set reflects the override without changing tool exposure
  for unrelated nodes.
- Given an override that removes a tool required by a `tool_use_step`, when
  workflow preparation runs, then the library fails closed with a clear validation
  error instead of allowing execution to reach an unresolved tool invocation.
- Given a tool id appears only in the generated manifest or optional tool index
  but not in the effective registry, when execution preparation requires that
  tool, then the library fails closed because metadata alone cannot satisfy a
  callable tool dependency.

### FR-3c: Provide opt-in built-in tool packs

The runner may provide built-in tool implementations as explicit opt-in registry
packs. Built-in tools are never ambient global capabilities: callers must enable
the pack, and workflow nodes must still reference the relevant tool ids before a
tool is exposed or invoked.

Acceptance criteria:

- Given the caller enables the read-only `local_workspace` tool pack, when
  registry preparation runs, then the effective registry includes conservative
  file-inspection tools such as `read_file`, `list_files`, `search_files`,
  and `inspect_path` constrained to approved workspace roots.
- Given the caller does not enable a built-in tool pack, when a node references
  a built-in tool id, then the tool is unavailable unless the caller registered
  an equivalent tool explicitly.
- Given a write-capable built-in tool pack is introduced, when it is enabled,
  then tools such as `write_file`, `patch_file`, `create_directory`, or
  `delete_path` must be separately opt-in, path-restricted, and approval-aware by
  default.
- Given command-execution tools are introduced, when they are enabled, then tools
  such as `run_command`, `run_tests`, or `run_linter` must use allowlisted
  commands, timeout limits, working-directory restrictions, and side-effect
  metadata.
- Given a workflow references built-in tools, when schema conversion runs, then
  those tools are converted through the same registry-to-OpenAI schema path as
  caller-registered tools.

### FR-4: Run workflow from a user prompt

The library must accept a user prompt and use it as the initial request for the
configured workflow.

Acceptance criteria:

- Given a valid workflow and prompt, when the caller invokes execution, then the
  workflow runs from that prompt.
- Given an empty or invalid prompt, when the caller invokes execution, then the
  library rejects the request with a clear validation error.

### FR-5: Return the final workflow result

The library must return the final result produced by the workflow.

Acceptance criteria:

- Given successful workflow execution, when the workflow completes, then the
  caller receives the final result.
- Given partial failure, when the workflow cannot complete, then the caller
  receives an error rather than a misleading final result.

### FR-6: Expose a CLI

The repository must expose a command-line interface in addition to the library
API.

Acceptance criteria:

- Given paths to `agent-design.md`, `agent-runtime.yaml`, `agent-graph.mmd`, and
  optional `tool-index.yaml` metadata, when a user runs the CLI with a prompt and
  a configured registry source, then the CLI loads the package and returns the
  final workflow result.
- Given invalid or inconsistent artifacts, when a user runs the CLI, then the CLI
  exits non-zero and reports the validation error clearly.
- Given a workflow that expects tool use, when a user runs the CLI without a
  configured tool registry, then the CLI fails clearly instead of silently
  ignoring tool steps.

## Non-Functional Requirements

- The library must be testable without requiring live model calls in unit tests.
- Artifact parsing and workflow execution should be separated enough to test
  validation independently from execution.
- Runtime dependencies must include the official `openai` package because the
  initial default model execution path is built on OpenAI's Python SDK.
- `ocihelper` must not be a required runtime dependency. The project may
  replicate needed runtime behavior locally rather than depending on
  `ai-tools-core` or adjacent ecosystem packages.
- The implementation must support Python `>=3.11,<3.14` as declared in
  `pyproject.toml`.
- The library should avoid hard-coding machine-specific producer paths into
  runtime behavior; the recorded paths are provenance and local source context.
- Runtime execution must honor manifest execution-policy constraints such as
  autonomy level, allowed execution modes, approval-required actions, forbidden
  actions, maximum iterations, and timeout when those values are known.
- Runtime consumers must fail closed when required fields are missing, node kinds
  are unsupported, decision subtype names are unsupported, or edge semantics are
  unsupported for the manifest `format_version`.
- Initial implementation must support only `format_version: 1` for runtime
  manifests and for external tool-index metadata when such metadata is supplied.
- Safety, authentication, logging, and redaction rules are expected to be refined
  during the first implementation. Some of those rules may become part of the
  workflow specification itself; until then, runtime behavior must avoid
  over-claiming unimplemented safety guarantees.
- Initial implementation should favor the official OpenAI Python client,
  OpenAI-compatible model semantics, and a repository-owned tool registry and
  tool-call convention mapping.

## Observed Runtime Manifest Shape

The runtime package includes `agent-design.md`, which references the runtime
manifest and Mermaid graph. Runtime loading must treat these three artifacts as
one package-level consistency boundary.

The runtime package reference describes `agent-runtime.yaml` as the structured
source of truth for runtime construction and `agent-graph.mmd` as a Mermaid view
derived from the YAML. For `format_version: 1`, required top-level manifest
fields are:

- `format_version`
- `package_type`
- `package_id`
- `entrypoint`
- `packaging`
- `nodes`
- `edges`

Optional but recommended top-level fields include:

- `name`
- `description`
- `mermaid_diagram`
- `patterns_present`
- `execution_policy`
- `state`
- `skills`
- `tools`
- `participant_groups`
- `modes`
- `phases`
- `roles`
- `output_contracts`
- `validation`

The example runtime YAML has this high-level shape:

```yaml
format_version: 1
package_type: dynamic_agent_design
package_id: simple-tool-agent
name: Simple Tool Agent
entrypoint: analyze_request
mermaid_diagram: simple-tool-agent-graph.mmd
packaging: ...
patterns_present: ...
execution_policy: ...
state: ...
skills: ...
tools: ...
participant_groups: []
modes: ...
phases: ...
roles: ...
nodes: ...
edges: ...
output_contracts: ...
validation: ...
```

Observed node kinds in the example are:

- `llm_step`
- `tool_use_step`
- `decision_step` with `decision_subtype: llm_route`

The runtime package reference also allows these decision subtypes:

- `tool_response_compare`
- `simple_check`
- `llm_route`

Observed edge kinds are:

- `sequential`
- `branch`

The runtime package reference also defines these `format_version: 1` edge kinds:

- `sequential`
- `branch`
- `loopback`
- `parallel_fanout`
- `parallel_join`
- `event`
- `capability`

Control-flow execution should use control-flow edges. Tool availability should
use capability overlay edges so capability display is not confused with actual
tool invocation.

## Supported Pattern Metadata

The agent-development skill now documents the supported primary agent pattern
IDs in `references/examples/agent-pattern-examples.md`. Runtime consumers should
treat these IDs as coarse design-classification metadata rather than as new
primitive execution node kinds:

- `basic-reasoning-agent`
- `tool-based-function-calling-agent`
- `tool-server-or-mcp-style-agent`
- `computer-use-agent`
- `coding-agent`
- `speech-or-voice-agent`
- `workflow-orchestration-agent`
- `memory-augmented-agent`
- `simulation-or-test-bed-agent`
- `observer-or-monitoring-agent`
- `multi-agent-collaboration`

Initial loader and model work must preserve these pattern IDs when they appear
in `patterns_present`. Initial execution compatibility may remain narrower than
the full pattern catalog, but parsing must not discard pattern metadata merely
because concrete adapters for a pattern are not implemented yet.

For `format_version: 1`, documented pattern shapes should still compile down to
the small primitive execution taxonomy:

- `llm_step`
- `tool_use_step`
- `decision_step`

Pattern-specific structure should be represented with metadata and graph fields
such as `participant_groups`, `roles`, `modes`, `phases`, `state`,
`execution_policy`, `available_tools`, and control-flow edge kinds including
`loopback`, `parallel_fanout`, `parallel_join`, `event`, and `capability`.
Examples:

- Multi-agent collaboration should use participant groups, role nodes, parallel
  or batched LLM steps, join or synthesis nodes, and decision gates rather than
  a `multi_agent_step` node kind.
- Memory-augmented agents should use retrieval or memory tools, state metadata,
  confidence decisions, and synthesis LLM steps rather than a `memory_step` node
  kind.
- Computer-use, speech or voice, observer, simulation, and tool-server patterns
  should expose their capabilities through declared tools, policy metadata,
  phases, events, and ordinary primitive nodes until a later format version
  defines stronger semantics.

## Tool Index Shape

The runtime manifest may inline tool metadata under top-level `tools`. A separate
reusable `tool-index.yaml` may also be used when multiple manifests share a
portable metadata catalog. Neither source is sufficient to make a tool callable;
the effective registry remains authoritative for executable tool adapters.

The observed external tool index has this high-level shape:

```yaml
format_version: 1
index_type: agent_runtime_tool_index
index_id: example-tool-index
name: Example Tool Index
usage:
  default_import_mode: referenced_by_manifest
  compatible_runtime_manifest_versions:
    - 1
tools:
  - id: search_repo
    label: Search repository
    description_for_llm: ...
    adapter: runtime.search_files
    input_schema: ...
    output_schema: ...
    side_effect: read
    approval_required: no
    timeout: runtime_default
    retry_policy: bounded
    failure_behavior: fallback
    skill_bindings: ...
skills:
  - id: agent-development
    source_type: repo_skill
    source_path: skills/agent-development-skill/SKILL.md
    packaging_mode: referenced_only
```

Observed tool metadata entries in the example index:

- `search_repo` using adapter `runtime.search_files`
- `read_file` using adapter `runtime.read_file`
- `validate_runtime_manifest` using adapter `scripts.validate_agent_runtime`

Supported side-effect and policy fields should include `side_effect`,
`approval_required`, `timeout`, `retry_policy`, and `failure_behavior`.

Runtime tool overrides may layer on top of manifest metadata, optional external
tool-index metadata, and the supplied registry. The initial override model should
support adding new registered tool definitions, replacing an existing registry
tool definition by id, disabling a tool by id, and restricting or extending the
tools exposed to a specific `llm_step`. These overrides are runtime inputs and
must not require edits to `agent-design.md`, `agent-runtime.yaml`,
`agent-graph.mmd`, or the reusable `tool-index.yaml`.

Built-in default tools may be provided as explicit opt-in registry packs. The
initial built-in pack should be read-only and local-workspace scoped, with tools
such as `read_file`, `list_files`, `search_files`, and `inspect_path`. Write and
command execution tools should live in separate, more restrictive packs and must
not be enabled implicitly.

## Tool Registry and OpenAI Package Interfaces

Initial model execution support will use the official `openai` package from
`https://pypi.org/project/openai/`. The implementation should call the OpenAI
Python SDK directly through a small runtime-owned adapter boundary so unit tests
can replace live model calls with a fake or stub client.

Initial tool registry support will be implemented in this repository rather than
delegated to `ai-tools-core`. The registry pattern should combine callable tool
adapters with manifest or optional tool-index metadata where useful, then expose
runtime-callable tools and the OpenAI tool schema shape needed for model tool
calls. A tool listed only in manifest or tool-index metadata is not executable
until the effective registry provides a callable adapter for that tool id.

The runtime should start with OpenAI package model and client interfaces:

- Default model execution uses a library-owned execution path backed by the
  official `openai` package.
- Optional chat-client injection should target a protocol compatible with the
  subset of OpenAI SDK behavior needed by the runtime executor.
- Tool registry injection should target this repository's own registry protocol,
  including tool lookup by manifest `tool_id`, conversion to OpenAI tool schema,
  invocation dispatch, side-effect metadata, approval metadata, timeout/retry
  policy, and structured result or failure reporting.
- Registry preparation should accept runtime tool overrides that add, replace,
  disable, or restrict tools globally or for individual `llm_step` nodes while
  preserving the generated artifacts as the unmodified baseline.
- Registry preparation may accept caller-enabled built-in tool packs that
  pre-register default tools, while preserving explicit node references as the
  only way those tools become available to a workflow step.

## Assumptions

- The generated runtime YAML is the primary workflow-definition artifact.
- The Mermaid diagram is referenced by the runtime YAML and should be treated as
  a derived validation/documentation artifact.
- Initial support is limited to `format_version: 1` for runtime manifests and
  optional tool-index metadata.
- Tool metadata may be inline in the runtime manifest under `tools` or loaded
  from a reusable external `tool-index.yaml` catalog, but callable tool
  availability is determined by the effective registry.
- If workflow execution is expected to invoke tools, the caller provides an
  repository-owned tool registry argument or approved registry source.
- Built-in default tool packs are disabled unless explicitly enabled by the
  caller, and enabling a pack does not expose tools unless nodes reference them.
- Runtime tool overrides are caller-provided execution/preparation inputs layered
  over generated artifacts; they do not mutate or replace the authoritative
  generated agent-design package.
- The library constructs and owns the default OpenAI package execution path,
  while allowing an optional protocol-similar client to be passed in.
- Initial implementation starts with the official OpenAI Python package and
  OpenAI-compatible model semantics.
- Supported agent patterns are manifest metadata for initial loader/model work;
  they do not imply that every pattern has full executor or adapter support in
  the first implementation.
- Safety, authentication, logging, and redaction requirements will be discovered
  during the first implementation and may be promoted into workflow-spec fields.

## Suggested Public API Shape

The README records this conceptual shape:

```python
from dynamic_agent_runner import run_agent_workflow

result = run_agent_workflow(
    agent_design="path/to/agent-design.md",
    definition_yaml="path/to/agent-definition.yaml",
    mermaid_diagram="path/to/workflow.mmd",
    tool_index="path/to/tool-index.yaml",  # optional metadata
    prompt="Run the workflow for this user request.",
    tool_registry=registry,
    chat_client=None,
)
```

This is design intent only. The concrete parameter names should be finalized
during technical planning. The initial `tool_registry` design should use this
repository's own registry pattern, and `chat_client` should be compatible with
the runtime's OpenAI client protocol.
